This Document in Plain English

If you've ever filled out a Salesforce record, you already understand 90% of what an ontology is. This document just names the things we work with every day and shows how they connect.

What is an Ontology?

An ontology is a shared vocabulary. It names every "thing" in a system, what properties each thing has, and how things relate to each other. Think of it as the blueprint for how Cortex understands the consulting world.

Analogy: A Salesforce org has Accounts, Contacts, Opportunities, Activities. Each has fields. They connect via lookups. That's Salesforce's ontology. This document is Cortex's version — but for consulting work, not CRM data.

Entities = The Nouns

An entity is a "type of thing" that exists in the system. Each entity has attributes — the fields that describe it. Every specific instance (like "Client B" or "the CLIENT-A Wealth Assessment") is a row in that entity's table.

Entity: Client
Attributes: name, industry, geography, asset_size, tech_stack
Instance: name="Client B CU", industry="Credit Union", geography="North America", asset_size="$170B+"

We have 32 entities organized into 5 categories:

Reference Data — Domain knowledge that exists before any engagement (templates, taxonomies, personas)
Core — The actors and containers (clients, consultants, engagements, files)
Events — The timeline of what happened, when, and why (append-only, immutable)
Artifacts — Work products from engagements (discoveries, scores, journey maps, use cases, ROI models)
Intelligence — Patterns that emerge across many engagements (benchmarks, pain patterns, outcomes)

Relationships = The Verbs

Relationships describe how entities connect. Each relationship has a direction (forward and inverse) and a cardinality — how many of one thing can connect to how many of another.

Forward: Client hasEngagement Engagement (one client can have many engagements)
Inverse: Engagement isEngagementOf Client (each engagement belongs to one client)
Cardinality: 1 → N (one-to-many)

The special relationship: EngagementEvent has a caused_by_event_id that points to ITSELF. This creates causal chains — you can trace "the plan changed because the debrief revealed the CFO was engaged, which happened because Workshop 1 was completed." Every consequence links back to its cause.

Events = The Journal

An event is an immutable record of something that happened at a specific moment. Events are append-only — once written, they never change. There are 20 types of events (workshop completed, plan modified, client decision, etc.).

Feb 12: workshop_completed — "Strategic Alignment" (actor: consultant)
Feb 14: debrief_submitted — "CFO showed up unexpectedly" (actor: consultant)
Feb 14: plan_modified — "Added ROI framing to Workshop 2" (actor: system, caused by the debrief)
Analogy: Git commits. Each commit is immutable, has a timestamp, a message, and a parent commit. Events work the same way — each has a timestamp, a description, and optionally a "caused by" pointer to its parent event.

Enumerations = The Dropdowns

An enumeration (enum) is a fixed list of allowed values. Like a dropdown menu — you can only pick from the defined options. This ensures everyone uses the same vocabulary.

domain: retail | commercial | wealth | investing | sme
journey_stage: why_change | why_now | why_invest | why_stay
severity: critical | high | medium | low

Class Hierarchy = Inheritance

Some entities share common properties. Instead of repeating engagement_id and created_at on every entity, we define a parent class that children inherit from.

EngagementArtifact (abstract parent) has: engagement_id, domain, created_at
↓ inherited by
JourneyMap, ProcessMap, CapabilityScore, UseCase, ROIModel, etc.

This means every artifact automatically has engagement_id — you don't have to remember to add it.
Analogy: In banking, a "Financial Product" is the parent. "Savings Account", "Current Account", "Fixed Deposit" are children. They all have account_number and balance (inherited), but each adds its own fields (interest_rate, overdraft_limit, maturity_date).

Current State vs Target State

Several artifacts exist in pairs: what the client has TODAY vs what we recommend for THE FUTURE. The gap between them is literally the engagement — understanding current, defining target, quantifying the delta, building the case to close it.

ProcessMap (current): "Lending takes 3.2 days, 9 manual steps, 22% STP"
ProcessMap (target): "Lending takes 4 hours, 2 manual steps, 85% STP"

JourneyMap (current): "Customer visits branch 3 times, 35% abandon"
JourneyMap (target): "Fully digital, zero branch visits, 85% completion"

The delta feeds directly into ValueLever → ROIModel → Roadmap.

The Full Chain — How Everything Connects

The power of the ontology is traceability. Every number in the business case traces back to a specific finding from a specific workshop:

Workshop (Capability Assessment) →
  surfaces Discovery ("50% accounts never funded" — pain_point, critical) →
    reveals gap in CapabilityScore ("Activation Orchestration: 0.8/4.0") →
      addressed by UseCase ("Guided Account Funding" — must_have, lighthouse) →
        drives ValueLever ("Funded account increase: $3.2M/year") →
          rolled into ROIModel ("Conservative NPV: $4.2M") →
            sequenced in RoadmapPhase ("Phase 1: 6 months, $800K") →
              presented at Workshop (Executive Readout) →
                leads to Decision ("CFO: proceed with Phase 1") →
                  detected as Outcome ("reached_negotiation")

Knowledge Source Lifecycle

Day 0 — Seeded: Domain knowledge files (pain_points.md, benchmarks.md) are parsed into PainPattern and Benchmark rows with source_type: seeded, low confidence.

External ingestion: A consultant drops a McKinsey PDF. LLM extracts benchmarks and pain points. Items are created with source_type: external, high confidence but generic. An ExternalSource record tracks the publication.

Engagement validation: Real engagement discovers the same pain point or measures the same metric. Discovery links to PainPattern via isInstanceOf. Source becomes hybrid. Confidence increases. Range sharpens from estimates to real data.

Convergence: When seeded + external + engagement data all agree, that's the highest confidence. "McKinsey says 35-55%. Our own data from 18 engagements shows 38-52%. The benchmark is now validated."

Intelligence Queries

The questions the knowledge base must answer. Each shows the entity traversal path.

1. "What workshop sequences worked for situations like mine?"
Embedding (cosine similarity on engagement profile) → EngagementPlan (get workshop sequence) → Workshop (types, order, adaptations) → Outcome (reached_negotiation or closed_won) → return winning sequences ranked by similarity
2. "What pain points should I probe for in this segment?"
PainPattern (filter by industries + domains, ORDER BY frequency) → Discovery (contributing instances with severity + impact) → return patterns with real examples
3. "What ROI ranges are realistic for digital onboarding?"
ValueLever (filter by lever_name LIKE 'onboarding') → ROIModel → Outcome (did the deal close?) → return ranges: AVG(annual_value), MIN, MAX, with confidence based on sample size
4. "Trace back: what caused this deal to expand?"
Outcome (expanded) → EngagementEvent (scope_change) → recursive caused_by_event_id traversal → returns full chain: debrief → plan adaptation → workshop → original Q&A
5. "When consultants face a skeptical CTO, what do they change?"
EngagementChoice (WHERE reason ILIKE '%CTO%' OR reason ILIKE '%skeptic%') → GROUP BY action_type + action_data → most common: workshop_reordered (Architecture moved up)
6. "What's the average capability score for credit unions in investing?"
CapabilityScore (JOIN Engagement JOIN Client WHERE industry='Credit Union' AND domain='investing') → GROUP BY capability_name, layer → AVG(current_score), PERCENTILE → compare to Benchmark
7. "Which engagements are most similar to my current situation?"
Embedding (source_type='engagement_profile') → pgvector cosine similarity <=> → JOIN Engagement → JOIN Outcome → return ranked matches with what happened + what workshops were run
8. "Which use cases are most commonly chosen as lighthouse?"
UseCase (WHERE is_lighthouse=true) → GROUP BY template_id → JOIN UseCaseTemplate → return: name, frequency, avg effort_weeks, avg priority_score, domains
9. "What applications do clients typically consolidate when adopting Backbase?"
Application (WHERE disposition='consolidate') → GROUP BY category, vendor → return: most common consolidation targets with frequency and avg savings
10. "What's the journey friction → process bottleneck → ROI connection?"
JourneyMap (friction_points) → ProcessMap (linked via linked_journey_ids, bottleneck steps) → CapabilityScore (gaps) → UseCase (solutions) → ValueLever ($ impact)
